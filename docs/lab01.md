1. Le projet contient **3 modules Gradle** : `:androidApp`, `:desktopApp` et `:shared`. Ils sont déclarés dans `settings.gradle.kts` avec trois appels à `include(...)`. `iosApp` n'en fait pas partie : c'est un projet Xcode natif (Swift/Objective-C) qui consomme le framework produit par `shared`, mais ce n'est pas un sous-projet Gradle.

2. Les versions sont définies dans `gradle/libs.versions.toml` : Kotlin **2.4.21**, Compose Multiplatform **1.12.2** et Android Gradle Plugin (AGP) **9.1.1**. La version de Gradle est **9.5.1**, indiquée par `gradle/wrapper/gradle-wrapper.properties`.

3. `shared/build.gradle.kts` applique les plugins Kotlin Multiplatform, Android Kotlin Multiplatform Library, Compose Multiplatform et Compose Compiler. `androidApp/build.gradle.kts` applique Android Application et Compose Compiler. Il n'applique pas `org.jetbrains.kotlin.android` car, avec AGP 9, la prise en charge de Kotlin Android est intégrée à AGP ; le plugin Kotlin Android séparé n'est donc plus nécessaire.

4. Le `minSdk` de la bibliothèque partagée est configuré dans le bloc `kotlin { android { ... } }` de `shared/build.gradle.kts`. Celui de l'application est configuré dans `android { defaultConfig { ... } }` de `androidApp/build.gradle.kts`. Dans les deux cas, la valeur vient du catalog (`libs.versions.android.minSdk`), et n'est pas écrite en dur ; le catalog fixe cette valeur à **36**.

5. Les dossiers de `shared/src/` sont `commonMain`, `commonTest`, `androidMain`, `androidHostTest`, `iosMain`, `iosTest`, `jvmMain` et `jvmTest`. Il n'y a pas de `iosArm64Main` car Kotlin Multiplatform utilise la hiérarchie par défaut : `iosMain` est un source set commun aux cibles iOS `iosArm64()` et `iosSimulatorArm64()`.

6. `expect fun getPlatform()` est déclarée dans `shared/src/commonMain/kotlin/fr/m2/pokequiz/Platform.kt`. Il existe **3** fonctions `actual` : dans `shared/src/androidMain/kotlin/fr/m2/pokequiz/Platform.android.kt`, `shared/src/iosMain/kotlin/fr/m2/pokequiz/Platform.ios.kt` et `shared/src/jvmMain/kotlin/fr/m2/pokequiz/Platform.jvm.kt`.

7. L'`applicationId` Android est `fr.m2.pokequiz`, dans `androidApp/build.gradle.kts`. La `mainClass` desktop est `fr.m2.pokequiz.MainKt`. Le suffixe `Kt` vient du fait que la fonction `main` est déclarée dans le fichier Kotlin `main.kt` au niveau supérieur ; le compilateur génère alors une classe JVM nommée `MainKt`.

8. La fonction `App()` est définie dans `shared/src/commonMain/kotlin/fr/m2/pokequiz/App.kt`. Elle est appelée depuis **4 endroits** : `MainActivity.kt` (dans `setContent`), `MainActivity.kt` (dans `AppAndroidPreview`), `desktopApp/src/main/kotlin/fr/m2/pokequiz/main.kt` (dans la fenêtre desktop) et `shared/src/iosMain/kotlin/fr/m2/pokequiz/MainViewController.kt` (dans le contrôleur iOS).

9. Le `.gitignore` généré ignore notamment les fichiers `.iml`, `.kotlin`, `.gradle`, les dossiers `build/`, `xcuserdata`, `local.properties`, `.idea`, `.DS_Store`, les captures, les fichiers de build natif (`.externalNativeBuild`, `.cxx`), les fichiers Xcode générés et `node_modules/`. `local.properties` doit être ignoré car il contient des chemins propres à la machine, notamment `sdk.dir`, et ne peut donc pas être partagé de façon portable ; il peut aussi révéler l'organisation locale des fichiers.

10. Dans `shared/src/commonMain/.../App.kt`, l'IDE signale une erreur du type **Unresolved reference: `java`** (ou `File`). `java.io.File` appartient à la bibliothèque standard de la JVM et n'est donc pas disponible dans `commonMain`, dont le code doit pouvoir être compilé pour toutes les plateformes, notamment iOS. Il faudrait placer ce code dans `jvmMain` ou utiliser une abstraction `expect`/`actual` avec une implémentation spécifique à chaque plateforme.

11. Après avoir incrémenté le compteur puis fait pivoter l'émulateur Android, le compteur revient à **0** : il n'est pas conservé. La rotation recrée l'activité et l'état déclaré avec `remember` est réinitialisé ; il faudrait utiliser `rememberSaveable` (ou un ViewModel) pour conserver cette valeur lors d'un changement de configuration.

## Questions complémentaires

1. Développer l'interface sur Desktop permet d'obtenir un cycle de compilation et d'exécution beaucoup plus rapide qu'avec un émulateur Android ou un appareil. On peut tester l'interface avec une souris et un clavier, sans attendre le déploiement mobile. La cible Desktop est donc un outil de développement et de validation, même si le livrable final est mobile ; les tests Android et iOS restent nécessaires pour les comportements propres à ces plateformes.

2. Le Hot Reload recharge dans une application déjà lancée les classes ou le code modifié qui sont compatibles avec le rechargement. Un redémarrage arrête puis relance complètement l'application et recrée son état. Il faut notamment redémarrer après une modification de la configuration Gradle, des plugins, des dépendances, des cibles/source sets ou de la classe `main`. Un changement de ressources ou de code non pris en charge par le Hot Reload peut aussi imposer un redémarrage.

3. Le bloc `androidTarget {}` appartient aux anciennes versions ou à une autre configuration du plugin Kotlin Multiplatform. Dans ce projet, le plugin `com.android.kotlin.multiplatform.library` et AGP 9 utilisent le bloc `android {}` dans `shared/build.gradle.kts`. Ajouter tel quel le bloc d'un tutoriel de 2023 peut donc produire une référence DSL inconnue, une configuration de cible en double ou des erreurs de compatibilité de plugins. Il faut adapter le tutoriel aux versions du projet plutôt que cumuler les deux syntaxes.

4. `Greeting` est dans `commonMain` et appelle la fonction `expect fun getPlatform()`. Chaque source set de plateforme fournit une fonction `actual` portant la même signature : Android, JVM Desktop et iOS. Le compilateur lie l'appel commun à l'implémentation de la cible en cours de compilation. Le texte varie donc selon `Platform.name`, bien que le code de `Greeting` soit partagé.

5. Sur Android, le bytecode Kotlin/Java est transformé en DEX ; sur Desktop, il devient du bytecode JVM dans des fichiers `.class` ; sur iOS, Kotlin/Native produit du code natif dans un framework. Le bytecode JVM est généralement le plus facile à décompiler et à analyser. Dans tous les cas, le code client peut être récupéré : un secret ou un algorithme sensible placé dans `commonMain` est donc distribué dans plusieurs artefacts et ne doit pas être considéré comme confidentiel. Les secrets et la logique critique doivent rester côté serveur.

6. La commande affiche notamment les tâches `jvmRun`, `hotRunJvm`, `hotDevJvm`, `hotRunJvmAsync`, `hotDevJvmAsync`, `hotReloadJvmMain` et `reload`. Les tâches directement liées au Hot Reload sont `hotRunJvm`/`hotDevJvm` pour lancer une application avec cette fonction, `hotReloadJvmMain` pour recharger la cible JVM principale et `reload` pour recharger les applications en cours. `jvmRun` lance simplement la cible JVM sans être la tâche Hot Reload principale.

7. Après `:shared:jvmJar`, les classes JVM se trouvent notamment dans `shared/build/classes/kotlin/jvm/main/`, organisées selon le package, et le JAR est produit dans `shared/build/libs/`. Les sorties Android sont dans `shared/build/classes/kotlin/android/main/`. Les fichiers `.klib` ne sont pas des classes JVM : ce sont des bibliothèques Kotlin/Native ou des artefacts intermédiaires de compilation, à rechercher dans les répertoires `build` associés aux compilations natives. Ils contiennent du code compilé et des métadonnées pour une cible Native, alors que les `.class` correspondent à la cible JVM.

8. L'arbre `jvmRuntimeClasspath` fait apparaître `org.jetbrains.compose.ui:ui` puis `ui-desktop`, qui amène les composants de rendu Desktop et, transitivement, Skiko. Skiko fournit le moteur de rendu graphique multiplateforme basé sur Skia utilisé par Compose Desktop. Sa présence est donc normale : elle vient de l'implémentation Desktop de Compose et non d'un appel direct dans le code applicatif.

9. Les preflight checks contrôlent notamment la cohérence de l'environnement, des cibles et des outils avant une compilation Native, puis peuvent signaler une configuration iOS incomplète ou une version incompatible. Sur Windows, les tâches iOS ne peuvent pas s'exécuter : Gradle signale par exemple que les tests du simulateur iOS nécessitent macOS. Sur Mac, désactiver puis réactiver le contrôle permet de comparer un build sans cette vérification et un build qui la réexécute. Cela ne rend pas iOS exécutable sur Windows et ne remplace pas les vérifications Xcode, de signature et de simulateur.
